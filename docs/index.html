API de Detecção de Fraude

Como construir um buscador de vizinhos em Zig para 3 milhões de vetores em 150 MB e <1ms
Zig 0.16 · IVF K-Means++ · SIMD AVX2 · f16 · Unix Sockets
Rafael Sales · github.com/dmux

O Problema

Dado uma transação com ~14 atributos, decidir em millisegundos se é fraude.

A abordagem: comparar com 3 milhões de transações históricas rotuladas (fraude / legítima) e ver quais as 5 mais parecidas.

Se ≥ 3 das 5 são fraudes → nega.

k-Nearest Neighbors — algoritmo de classificação por votação dos vizinhos mais próximos.

Restrições de hardware

  • 2 instâncias da API: 0,45 CPU · 150 MB cada
  • Nginx: 0,10 CPU · 50 MB
  • Total: 1 CPU / 350 MB

Fórmula de score

score_p99 = 1000 × log₁₀(1000 / p99_ms)
score_det = 1000 × log₁₀(1/ε) − 300 × log₁₀(1+E)
total (máx) = 3000 + 3000 = 6000 pts

Por que Zig?

O gargalo é computacional puro: calcular distâncias L2 para centenas de milhares de vetores em <1ms. Precisamos de:

Sem GC

Qualquer pausa de garbage collection — mesmo 2ms — destrói o score_p99. Go, Java, e runtimes JIT são inviáveis.

Controle de memória

Com 150 MB de limite, precisamos saber exatamente quanto cada estrutura consome — sem surpresas do runtime.

SIMD nativo

Zig expõe vetores SIMD como tipos de primeira classe. O compilador emite AVX2/FMA/F16C sem bibliotecas externas.

Em C seria necessário escrever intrinsics manualmente (_mm256_fmadd_ps). Em Zig, escreve-se código idiomático e o compilador faz a vetorização.

Zig: Alocadores Explícitos

Em Zig, não existe alocação implícita. Toda função que aloca memória recebe um std.mem.Allocator como parâmetro.


// Em Go: make([]float32, n)  ← runtime decide onde e quando
// Em Zig: é explícito — você escolhe o alocador e gerencia o tempo de vida

pub fn initFromFile(allocator: std.mem.Allocator, path: []const u8) !IvfStore {
    var store = IvfStore{};

    // Alocamos exatamente o necessário — sem surpresas de tamanho
    store.vectors = try allocator.alloc([14]f16, n_vectors);
    store.labels  = try allocator.alloc(u8,      n_vectors);
    store.centroids = try allocator.alloc([14]f32, n_clusters);

    // Ler direto do arquivo para a memória já alocada (sem buffer intermediário)
    try reader.readSliceAll(std.mem.sliceAsBytes(store.vectors));
    return store;
}

Isso elimina o pico de memória causado por um buffer temporário de leitura — crítico para caber em 150 MB.

Zig: Tipos de Vetor SIMD

O maior diferencial de Zig para este projeto: vetores SIMD como tipos nativos da linguagem.

Declaração


// Um vetor de 8 floats processado
// em paralelo por AVX2
const v: @Vector(8, f32) = undefined;

// Splat: preenche todos os lanes
const zeros = @splat(@as(f32, 0.0));

// Operações element-wise compilam
// para instruções vetoriais únicas
const sum = a + b;         // VADDPS
const prod = a * b;        // VMULPS
const diff = a - b;        // VSUBPS

Reduce e Select


// @reduce colapsa o vetor para um scalar
// Emite VHADDPS + VEXTRACTF128
const total = @reduce(.Add, v * v);

// @select é um blend condicional
// Emite VBLENDVPS (sem branch!)
const mask: @Vector(8, bool) = a > b;
const result = @select(f32, mask, a, b);

// Conversão f16→f32 automática
// com hardware F16C (VCVTPH2PS)
const f16v: @Vector(14, f16) = data.*;
const f32v: @Vector(14, f32) = f16v;

Com -Dtarget_cpu=haswell, o compilador emite VCVTPH2PS, VFMADD231PS e VHADDPS automaticamente.

Distância L2 em Zig — Código Real


fn l2Distance(query: *const [14]f32, stored: *const [14]f16) f32 {
    // Converte f16 → f32 em hardware (F16C: VCVTPH2PS, ~1 ciclo)
    const q: @Vector(14, f32) = query.*;
    const v: @Vector(14, f32) = stored.*;  // conversão implícita f16→f32

    // Máscara: −1.0 indica campo ausente em qualquer um dos dois vetores
    const absent_q = q < @splat(0.0);
    const absent_v = v < @splat(0.0);
    const absent   = absent_q | absent_v;

    // Zera dimensões ausentes (blend sem branch — VBLENDVPS)
    const qm = @select(f32, absent, @splat(0.0), q);
    const vm = @select(f32, absent, @splat(0.0), v);

    // Distância L2: ||q - v||²  (AVX2 + FMA)
    const diff = qm - vm;
    return @reduce(.Add, diff * diff);
}

14 dimensões processadas em 2 iterações AVX2 (8 lanes × 2). Sem loops, sem branches no caminho crítico.

Por que Busca Exata é Inviável

Brute-force

Calcular L2 para todos os 3 milhões de vetores a cada request.

3.000.000 × 14 floats × 4 bytes = 168 MB
só para armazenar — sem nem computar

Com 450 req/s por instância e 0,45 CPU:

3M comparações × ~5 ns cada = ~15 ms por request
p99 impossível de chegar em 1ms

A solução: indexar

Em vez de comparar com todos, dividir o espaço de vetores em regiões (clusters) e buscar só nas regiões mais próximas da query.

1000 clusters → busca nos 50 mais próximos
~150.000 vetores por request
20× menos comparações

Isso é o IVF — Inverted File Index.

IVF — Inverted File Index

O índice é construído em pré-processamento (build time). Em runtime, só fazemos lookups.

① Construção (offline)

1
Rodar K-Means++ nos 3M vetores para encontrar K=1000 centroides que "resumem" o espaço
2
Atribuir cada vetor ao centroide mais próximo → lista invertida por cluster
3
Salvar no formato binário: centroides + vetores ordenados por cluster
→

② Query (online, <1ms)

1
Calcular L2 para os 1000 centroides (SIMD rápido, sem RAM fria)
2
Selecionar os nprobe=50 clusters mais próximos
3
Varrer ~150k vetores desses clusters com AVX2, manter top-5 via min-heap
4
Votar: fraudes / 5 → fraud_score

K-Means++ — Por que Importa

K-Means encontra K centroides que minimizam a distância dos vetores ao seu centroide. A qualidade dos centroides determina o recall do IVF.

K-Means vanilla

  • Inicializa K centroides aleatoriamente
  • Pode começar com centroides agrupados na mesma região
  • Converge para mínimos locais ruins
  • Clusters desbalanceados → recall baixo
Exemplo ruim: 3 centroides em SP, nenhum no RJ

K-Means++

  • 1º centroide: aleatório
  • Cada centroide seguinte: escolhido com probabilidade ∝ d² ao centroide mais próximo já escolhido
  • Forçosamente distribui pelos extremos do espaço
  • Convergência mais rápida e estável
100 iterações K-Means++: E=7 (vs E=18 com 50 iter.)

K-Means++ em Zig — Inicialização


// Escolher novo centroide com probabilidade ∝ d²
// (algoritmo D² sampling do K-Means++)
fn sampleNextCentroid(
    vectors: []const [14]f16,
    centroids: []const [14]f32,
    rng: std.Random,
) usize {
    // Calcular d² de cada vetor ao centroide mais próximo
    var total_weight: f64 = 0;
    var weights = try allocator.alloc(f64, vectors.len);
    for (vectors, 0..) |*v, i| {
        var min_dist: f32 = std.math.floatMax(f32);
        for (centroids) |*c| min_dist = @min(min_dist, l2Distance(c, v));
        weights[i] = min_dist * min_dist;   // d²
        total_weight += weights[i];
    }

    // Amostra aleatória ponderada — vetores distantes têm maior chance
    var r = rng.float(f64) * total_weight;
    for (weights, 0..) |w, i| {
        r -= w;
        if (r <= 0) return i;   // ← este vetor vira o próximo centroide
    }
    return vectors.len - 1;
}

Por que f16? O Problema da Quantização

Com 3M vetores × 14 dimensões, o formato de armazenamento importa muito para RAM e para precisão.

Formato Bits Passo mínimo 3M × 14 (RAM) E medido Viável?
u881/254 ≈ 0,00442 MB 158 (e piora!) ✗ phantom neighbors
f1616~0,00183 MB 7 ✓ escolhido
f3232~10⁻⁷168 MB ~0 ✗ excede 150 MB

f16 é o sweet spot: 2× mais preciso que u8 no que importa, cabe na RAM, e hardware moderno converte f16→f32 em 1 ciclo (F16C).

Phantom Neighbors — O Bug Silencioso do u8

Como acontece

Quantização u8: mapear f32 ∈ [0,1] → inteiro 0–255.

Passo: 1/254 ≈ 0,004

Dois vetores com diferença de 0,003 em f32 ficam idênticos em u8.

Esses "vizinhos fantasma" disputam o top-5 com vetores realmente próximos.

Efeito perverso com IVF

Mais nprobe → mais clusters → mais vetores visitados → mais phantom neighbors entram no top-5.

u8:
nprobe=20 → E = 80
nprobe=50 → E = 158
nprobe=100 → E = 338 (piora!)

f16:
nprobe=10…60 → E = 7 (estável)

Streaming Load — Lendo o Índice sem Estourar a RAM

Problema

Índice f16 em disco: 83 MB

Leitura ingênua:


// Lê tudo para buffer temporário
const buf = try allocator.alloc(u8, 83_mb);
_ = try file.readAll(buf);

// Copia para estrutura alocada
@memcpy(store.vectors_bytes, buf);
allocator.free(buf);
83 MB (buf) + 83 MB (estrutura) = 166 MB
Excede o limite de 150 MB!

Solução: ler direto para a estrutura


// Aloca só o destino final
store.vectors = try allocator.alloc(
    [14]f16, n_vectors);

// Lê do arquivo diretamente
// para a memória já alocada
// Zero cópia intermediária
const bytes = std.mem.sliceAsBytes(
    store.vectors);
try reader.readSliceAll(bytes);
Pico de RAM: 83 MB ✓

std.mem.sliceAsBytes — converte [][14]f16 para []u8 sem cópia, permitindo leitura direta da struct pelo reader.

Zero Allocation no Hot Path

Em Zig, toda alocação é visível no código. Isso permite eliminar alloc/free do caminho crítico — que roda ~450×/segundo.

Antes


// Uma string nova alocada a cada request
const body = try std.fmt.allocPrint(
    allocator,
    "{{\"approved\":{s}," ++
    "\"fraud_score\":{d:.4}}}",
    .{ approved, score }
);
defer allocator.free(body);

alloc + free por request → fragmentação de heap, latência não-determinística

Depois

  "{\"approved\":false,\"fraud_score\":1.0000}",

// Ponteiro direto — zero alloc, zero cópia

Warmup: Pré-aquecendo o Cache da CPU

Por que importa

Índice f16: 83 MB

L3 cache de um Haswell: ~8–20 MB

Na inicialização, o índice inteiro está em RAM fria. As primeiras requisições sofrem cache misses de 50–100µs por acesso.

Primeiras 100 reqs: 5–15ms cada
Arruína o p99 do aquecimento

Solução: 300 queries ao inicializar


// Antes de abrir o servidor HTTP,
// aquecemos diferentes regiões do índice
var wi: u32 = 0;
while (wi < 300) : (wi += 1) {
    // Distribui uniformemente:
    // amount cresce por 33, km por 3
    // → cobre clusters em diferentes
    //   regiões do espaço de features
    dummy.transaction.amount =
        @as(f32, @floatFromInt(wi)) * 33;
    dummy.terminal.km_from_home =
        @as(f32, @floatFromInt(wi)) * 3;
    _ = try service.evaluate(&dummy);
}
First request ≈ last request

Infraestrutura: Onde os ms São Ganhos

Unix Domain Sockets

Nginx → API via socket Unix (/sockets/api1.sock), não TCP loopback.

TCP exige kernel buffers separados, checksum, sequencing. UDS é memória compartilhada direta.

−0,2 ms / request

CFS Throttling Fix

Docker limita CPU via CFS (Completely Fair Scheduler) com período de burst + pausa.

cpu_period=100ms: usa 45ms, para por 55ms.
cpu_period=10ms: usa 4,5ms, para por 5,5ms.

−50ms worst-case p99

Thread Pool = 2

httpz com 2 worker threads por instância.

Enquanto thread A executa o IVF search (~350µs), thread B já aceita e faz o parse da próxima requisição.

2× throughput sob carga

Bug do httpz: TCP_NODELAY em Unix Socket

Um bug de biblioteca descoberto na integração com Unix Domain Sockets.

O bug


// httpz tenta setar TCP_NODELAY
// no listener — mesmo quando é UDS
if (is_unix_socket) {
    // BUG: TCP_NODELAY não existe
    // em Unix socket — Linux retorna
    // EOPNOTSUPP → crash!
    try posix.setsockopt(
        listener,
        posix.IPPROTO.TCP,
        1,  // TCP_NODELAY
        &std.mem.toBytes(@as(c_int, 1))
    );
}

A correção (como patch)


// Em vez de try (propaga o erro),
// ignoramos silenciosamente:
// TCP_NODELAY é no-op em UDS de qualquer forma
posix.setsockopt(
    listener,
    posix.IPPROTO.TCP,
    1,
    &std.mem.toBytes(@as(c_int, 1))
) catch {};

A correção foi aplicada como patches/httpz-unix-socket-tcp-nodelay.patch no Dockerfile — sem modificar o código da aplicação nem do vendor.

Em Zig, catch {} descarta o erro explicitamente — fica visível no code review, diferente de exceções implícitas.

Lições Aprendidas

Bugs que quase passaram

  • Buffer overflow silencioso: array de heap top[32] estourava quando nprobe>32 em ReleaseFast — sem panic, resultado incorreto silencioso
  • Phantom neighbors com u8: E piora com mais nprobe — contraintuitivo, diagnosticado comparando com brute-force
  • TCP_NODELAY em Unix socket: httpz tenta setar opção TCP em socket Unix → EOPNOTSUPP → crash ao iniciar
  • Permissão do socket: nginx worker (user nginx) não conseguia escrever no socket criado com umask 022 → umask 000 no CMD

Decisões que valeram

  • Zig para este domínio: vetores SIMD nativos + sem GC = combinação ideal para busca vetorial em tempo real
  • f16 como sweet spot: 2× mais RAM que u8, mas elimina phantom neighbors completamente
  • cpu_period=10ms: sem mudar código, p99 cai 10× só ajustando o scheduler
  • Streaming load: ler direto para a estrutura final cabe em 150 MB onde double-buffer não cabe
  • Respostas pré-computadas: k=5 só tem 6 saídas possíveis — zero alloc no hot path com uma linha
